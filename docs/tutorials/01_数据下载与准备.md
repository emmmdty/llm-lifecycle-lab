### 2.2 软件基线

| 软件 | 版本要求 |
| --- | --- |
| Python | 3.12（3.10–3.12 均可，本项目锁定 3.12） |
| 包管理 | `uv`（唯一工具链，不使用 pip/conda 混合） |
| CUDA runtime | 13.0（由 PyTorch cu130 构建自带，不修改系统 CUDA） |
| PyTorch | train/eval: 2.13.0+cu130；quant: 2.12.0+cu130；serve: 2.11.0+cu130 |

#### 新手必读：这一堆版本号到底是什么意思？

先分清三样容易混淆的东西：

| 名词 | 是什么 | 谁来提供 |
| --- | --- | --- |
| 显卡驱动（driver） | 操作系统和显卡沟通的底层程序，版本如 580.xx | 系统预装，**不要动** |
| CUDA | NVIDIA 的并行计算平台，GPU 编程的"公共语言" | 由 PyTorch 自带（cu130 = 基于 CUDA 13.0 构建），不需要单独安装 |
| PyTorch（torch） | 深度学习框架，我们写代码用的工具库 | 我们通过 `uv pip install` 安装 |

`torch 2.13.0+cu130` 的读法是："torch 版本 2.13.0，构建时使用的 CUDA 是 13.0"。同一个驱动 580.xx 下，`+cu130` 结尾的 torch 都能运行。

#### 为什么四个环境的 torch 版本不一样（2.13 / 2.12 / 2.11）？

不是随便定的，而是**每个工具链对 torch 版本各有要求**：

| 环境 | 实际版本 | 谁决定的 | 为什么 |
| --- | --- | --- | --- |
| `.venv-train` | 2.13.0 | transformers / peft / trl | 这些库不限制 torch 上限，解析时自动装最新 |
| `.venv-eval` | 2.13.0 | lm-eval | 同上，评测库同样宽松 |
| `.venv-quant` | 2.12.0 | **llmcompressor 0.12.0** | 量化库声明了 `torch < 2.13` 的上限，装 2.13 会直接报依赖冲突 |
| `.venv-serve` | 2.11.0 | **vLLM 0.26.0** | vLLM 的 CUDA 扩展（连续批处理、attention 优化）在编译期绑定 torch API，必须用官方声明的**精确版本** |

简单说：**vLLM 最挑剔**（要精确版本）、**llmcompressor 次之**（有上限）、**训练/评测最宽松**（最新就行）。三者 CUDA 都是 13.0，只有 torch 包版本不同。

这正是本项目强制"四个环境互相隔离"的根本原因——如果只用一个环境，这些约束会互相打架，谁都装不全。

另外为什么必须用 CUDA 13：5090 的 compute capability 是 12.0（显卡的硬件"代号"，Blackwell 新架构），它需要较新的 CUDA 工具链才能发挥能力。compute capability 是硬件属性，用 `torch.cuda.get_device_capability()` 可以查。

## 3. 环境配置

### 3.1 为什么需要四个隔离环境

先理解两个概念：

- **虚拟环境（venv）**：一个独立的 Python 目录，里面装的包只对这个环境生效。可以把它想成"四个独立的工具箱"——训练一个箱子、评测一个箱子、量化一个箱子、部署一个箱子，谁都不会碰坏谁的扳手。
- **包（package）**：别人写好的代码库，比如 torch、transformers。装包就是把这些库放进某个环境里。

本项目有四个工具链，它们对 torch 的版本要求互相冲突（见 2.2 的表格：vLLM 要精确的 2.11，llmcompressor 最多 2.12，训练想用最新的 2.13）。如果全装进一个环境，装完这个那个就装不上。所以约定四个隔离环境，互不干扰：

![四个隔离环境](./images/01_env_isolated.png)

### 3.2 创建流程

```mermaid
flowchart TD
    A[uv venv 创建隔离环境] --> B[安装各自依赖]
    B --> C[uv pip check 一致性检查]
    C --> D[uv pip freeze 锁定版本快照]
    D --> E[GPU 可见性验证 nvidia-smi / torch.cuda]
    E --> F[BF16 matmul 无 NaN 验证]
    F --> G[模型 CPU 加载验证]
```

实际命令（以训练环境为例）：

```bash
cd llm-lifecycle-lab

# 1. 创建隔离环境（指定 Python 3.12）
uv venv .venv-train --python 3.12

# 2. 安装依赖（cu130 的 torch 需要指定 PyTorch 官方源）
uv pip install --python .venv-train/bin/python \
  "torch==2.13.0+cu130" \
  "transformers" "datasets" "peft" "trl" \
  --index-url https://download.pytorch.org/whl/cu130

# 3. 一致性检查：所有已装包互相兼容
uv pip check --python .venv-train/bin/python
# 输出: All installed packages are compatible

# 4. 冻结版本，作为可复现记录（每个环境保存一份）
uv pip freeze --python .venv-train/bin/python > reports/5090-train-freeze.txt
```

**逐条解释：**

1. **`uv venv`**：创建名为 `.venv-train` 的隔离环境。装在这个环境里的包不会污染系统 Python，其他环境也看不到。
2. **`uv pip install`**：把包装进指定环境（`--python` 参数指定装到哪个环境）。`--index-url` 指定下载源——cu130 版本的 torch 只有 PyTorch 官方源有。注意这里**没有指定版本**的库（如 transformers）会自动解析出"当前环境下不冲突的最新版本"。
3. **`uv pip check`**：检查当前环境里所有已安装的包**互相是否兼容**（比如 A 要 torch>=2.0，B 要 torch<2.13，两者同时满足就通过）。这是环境健康的体检报告，每次改依赖后都要跑。
4. **`uv pip freeze`**：把当前环境所有包的**精确版本号**（如 `torch==2.13.0+cu130`）保存到文件。将来环境坏了可以照着这个文件一键重建，这就是"可复现"的含义。

评测、量化、部署环境同理，各自装 `lm-eval`、`llmcompressor`、`vllm`。

> **规则**：禁止把 LLM Compressor、lm-eval 的 vLLM extra 和 vLLM 强装到同一环境。每次修改依赖后必须重新执行 `uv pip check` 并更新 freeze。

### 3.3 环境验证命令

装完环境不能直接开工，先做四个"体检"：

```bash
# 体检一：GPU 与 CUDA 可见性
nvidia-smi
.venv-train/bin/python -c "import torch; print(torch.cuda.is_available()); print(torch.cuda.get_device_capability(0))"
# 期望: True / (12, 0)
```

`torch.cuda.is_available()` 输出 `True` 说明 torch 能"看见"显卡；`get_device_capability()` 输出 `(12, 0)` 是这张卡（Blackwell 架构）的硬件代号，验证驱动、CUDA、torch 三者配合正常。

```bash
# 体检二：BF16 矩阵乘法无 NaN
.venv-train/bin/python -c "
import torch
x = torch.randn(512, 512, device='cuda', dtype=torch.bfloat16)
y = x @ x
print('bf16 matmul nan:', bool(torch.isnan(y).any()))
# 期望: bf16 matmul nan: False
"
```

**BF16 是什么**：一种"半精度"数字格式，内存只有 float32 的一半，训练大模型又快又省显存，但精度低、容易出 NaN（Not a Number，非法数值，一旦出现训练就毁了）。所以 5090 上必须先验证 BF16 计算正常——输出 `False` 代表没有 NaN，可以放心用。

```python
# 体检三：模型 CPU 加载验证（无需 GPU，检查权重与参数数量）
import torch
from transformers import AutoModelForCausalLM

model = AutoModelForCausalLM.from_pretrained(
    "models/Qwen3-0.6B-Base", torch_dtype=torch.bfloat16
)
print(f"params: {model.num_parameters() / 1e6:.1f}M")
# 期望: params: 596.0M
```

这是检查**下载的模型文件是否完整、能不能被正确读取**。`from_pretrained` 读取模型目录里的配置文件+权重文件；`num_parameters()` 数出参数量（596.0M = 5.96 亿参数）。能加载、参数数正确，说明模型文件没问题。这里特意在 CPU 上加载——环境体检不需要占用 GPU。

### 3.4 遇到的问题

- **`torch_dtype` 弃用警告**：新版 transformers 提示改用 `dtype` 参数，不影响功能，忽略即可。
- **flash-linear-attention 警告**：加载 Qwen3 系列时提示 fast path 不可用、回退到 torch 实现，因为没有安装 fla/causal-conv1d。对 0.6B 模型完全可用，不必安装。
- **非交互式 shell 找不到 `gh` 等新装工具**：工具安装在 `~/.local/bin` 而 PATH 未包含时，用全路径调用即可。

## 5. 数据治理

下载完的 raw 数据**不能直接训练**。原因有三个：**泄漏**（训练集和评测集内容重叠）、**重复**（同一文本出现几万次浪费预算）、**不可追溯**（不知道数据从哪来、能否使用）。

### 5.1 治理管线

```mermaid
flowchart LR
    R[data/raw] --> A[盘点] --> B[许可证] --> C[schema 检查] --> D[有界抽样]
    D --> E[清洗] --> F[去重] --> G[按分组切分] --> H[Parquet] --> I[token 统计] --> J[manifest]
```

每步的含义：

| 步骤 | 做什么 | 为什么 |
| --- | --- | --- |
| 盘点 | 列出文件、行数、字段 | 知道手里有什么 |
| 许可证 | 核对并记录授权 | 合规与可追溯 |
| schema 检查 | 确认字段齐全、类型正确 | 防止下游解析炸掉 |
| 有界抽样 | 只保留预算内的样本 | 小模型学习不需要全量 |
| 清洗 | 去空行、去垃圾字符 | 减少无效学习信号 |
| 去重 | 完全相同的记录只留一份 | 重复数据浪费预算 |
| 分组切分 | 按 prompt 哈希分桶后切分 | **防止泄漏** |
| Parquet | 统一列式格式落盘 | 高效、类型稳定 |
| token 统计 | 统计各 split 的 token 数 | 估算训练时长与预算 |
| manifest | 写一份完整清单 | 数据版本化，可复现 |

### 5.2 关键概念：分组切分（防泄漏）

以偏好数据 ultrafeedback 为例：一条记录是 `instruction + chosen(好回答) + rejected(差回答)`。如果先随机按行切分，同一个 instruction 的 chosen 可能进训练集、rejected 进验证集——模型在训练时就见过这道题，验证分数虚高。

```mermaid
flowchart TD
    subgraph 正确做法
        B1[instruction P 的全部回答] --> T1[train 或 validation 二选一]
        B2[instruction Q 的全部回答] --> T2[另一个堆]
    end
    subgraph 错误做法
        A1[P 的 chosen] --> V1[train]
        A2[P 的 rejected] --> V2[validation ✗ 泄漏]
    end
```

实现上：`hash(instruction) % 1000` 决定该 prompt 进入哪个桶，桶再映射到各 partition——同一个 prompt 永远只落在一个 partition。

### 5.5 遇到的问题

- **Parquet 读取 bug 导致全部去重**：早期读取函数用 `zip(列名, 行)` 构建字典，实际得到的是 `{"text": "text"}`——所有行变得相同，2,141,709 条被去重成 1 条。教训：**先取 1 条验证再全量跑**。
- **token 统计比预期慢**：逐个记录调用 tokenizer 非常慢；确认 Qwen3 走 fast tokenizer 后，批量编码 1 万条仅 0.3 秒，问题出在逐条调用而非 tokenizer 本身。
- **共享盘写入慢**：用 `ionice -c 3`（空闲优先级）在共享磁盘写 816MB parquet 花了约 7 分钟。这是共享服务器上的正确取舍——宁可慢，不挤占他人 I/O。
- **`HF_HUB_OFFLINE` 下 lm-eval 无法加载数据集**：offline 模式禁止访问 Hub，但评测需要数据。解决：用本地已物化的 jsonl 构造自定义 task（`dataset_kwargs.data_files` 指向本地文件），完全离线运行。

## 6. 常见问题

**Q1：为什么不用一个环境装下所有包？**
四个工具链对 torch 的版本要求互相冲突（如 vLLM 与 llmcompressor），混装必然出现 `uv pip check` 失败。

**Q2：没有 GPU 能学完这个教程吗？**
环境验证、数据下载与治理、Tokenizer 训练都可以在 CPU 完成；但预训练、微调等阶段需要 GPU。没有 GPU 时建议先学完数据与环境部分，其余部分阅读+小规模 CPU 实验。

**Q3：token 统计为什么用 Qwen 的 tokenizer？**
阶段 2 阶段自建 tokenizer 还没诞生。用官方 tokenizer 做代理统计足够估算训练预算；阶段 3 自建 tokenizer 后再回填精确值。

**Q4：下载总是失败怎么办？**
先检查网络与仓库信息，重试；大文件分小批次下载并校验 sha256；数据优先选 ModelScope 源。

**Q5：为什么 processed 里没有图像？**
图像体积大且下游（阶段 11 多模态）需要原图字节。processed 存文本与元数据，图像留在 raw，阶段 11 按索引从 raw 加载。

**Q6：治理结果不满意能重跑吗？**
能。管线是确定性的（seed 固定），改配置后重跑会得到相同划分；改 seed 才得到新划分。manifest 里记录了当时用的全部参数。
